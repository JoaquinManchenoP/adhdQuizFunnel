# Team Workflow & Task Board

This project uses three separate subagents, defined in `.claude/agents/`:
`frontend-design`, `backend-dev`, `qa-product-owner`. Each runs in its own isolated
context — they don't talk to each other directly, so the main session (you, Claude)
coordinates them using this file.

## The loop
1. **Plan:** Break the request into tasks below. Each task gets an owner
   (`frontend-design` or `backend-dev`), acceptance criteria, and status `todo`.
2. **Dispatch:** Delegate each task to its owning subagent by referencing the task ID
   below, not by re-describing the task from scratch. Tasks with no file overlap can be
   dispatched in parallel; if a task needs Backend's contract first, run Backend before
   Frontend (or have Frontend state its assumed contract explicitly).
3. **Review gate:** When a subagent marks a task `ready-for-qa`, delegate it to
   `qa-product-owner` before treating it as done. Never skip this, even for small changes.
4. **Feedback loop:** If QA returns `CHANGES NEEDED`, delegate back to the owning
   subagent with the QA notes attached. Repeat steps 3–4 until QA marks it `PASS`.
5. **Close out:** Once QA passes a task, mark it `done` below.

## Staying in your lane
- `frontend-design` owns anything client-side, UI, design, or marketing-facing.
- `backend-dev` owns anything server-side, API, database, or integration-related.
- `qa-product-owner` only reads code and writes status/feedback in this file.

If a task needs both a frontend and backend change, split it into two linked entries
below instead of letting one agent touch the other's territory.

## Ground rules
- A task is never "done" without a QA/PO `PASS`.
- Don't run `frontend-design` and `backend-dev` on the same files at the same time.
- Always point a subagent at its task ID here rather than re-describing the task.
